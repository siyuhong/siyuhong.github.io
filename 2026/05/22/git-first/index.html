Git 核心概念

四大工作区域

  • 工作区（Working Directory）：即我们的工程项目文件
  • 暂存区（Staging Area）：只能通过 git GUI 或 git shell 窗口显示，提交代码、解决冲突的中转站
  • 本地仓库（Local Repository）：只能在 git shell 窗口显示，连接本地代码跟远程代码的枢纽，不能联网时本地代码可先提交至该处
  • 远程仓库（Remote Repository）：保存在服务器上的仓库，例如 GitHub

基本工作流程

  flowchart LR
      A[工作区] -->|git add| B[暂存区]
      B -->|git commit| C[本地仓库]
      C -->|git push| D[远程仓库]
      D -->|git fetch| C
      C -->|git merge| A
      D -.->|git pull| A

分支合并

merge（推荐用于主分支合并）

rebase（推荐用于功能分支整理）

SmartGit等GUI

例如：分支 dev 合并至 main

  1. 检出分支 dev、main（保留至本地）
  2. 保证本地 dev、本地 main 代码与远程分支是一致的
  3. 当前分支切换至 dev
  4. 选中 main 分支，右键选择合并

一般选择合并到工作区，检查验证完毕再提交。

常见冲突类型：

  • 重命名文件合并冲突：需要通过 git rm / git add 解决
  • 增删文件可选择：右键 -> 解决 -> 采用我们的/采用他们的

手动合并

分别克隆两个分支的代码，使用 Beyond Compare 比较并手动合并，再 commit、push。

该方法在 git 分支图上不会留下合并记录，且手动合并的代码被认为是你提交的（可能突然背锅）。不太建议。

合并策略对比

策略特点适用场景
merge保留完整历史，产生合并提交主分支合并，需要保留分支历史
merge --no-ff强制产生合并提交功能分支合并到主分支
rebase线性历史，无合并提交功能分支整理，保持历史清晰
squash压缩多个提交为一个清理琐碎提交

注意：rebase 在 git 中是一个非常有魅力的命令，使用得当会极大提高自己的工作效率；相反，如果乱用，会给团队中其他人带来麻烦。

永远不要 rebase 已经推送到远程的提交！

多人协作流程

提交前先pull

预设场景：

  • 同事 A，同事 B
  • 初始远程仓库：版本 T

由于所有项目组成员都可以修改远程仓库的版本，很容易出现以下情况：

  • 同事 A、B 都 clone 了远程仓库版本 T，修改后的版本记录为 TA、TB
  • 假设同事 A 先提交，这时远程仓库变为 TA，同事 B 再提交代码时可能出现两个情况：
  1. Git 自动合并
  2. 需要手动解决冲突

提交代码前先从远程仓库同步代码，最后再推送至远程仓库！git pull --rebase
